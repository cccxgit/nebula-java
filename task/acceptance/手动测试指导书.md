# 数据搬迁与独立校验：真实集群手动测试指导书

本指导书对应 [task.md](../task.md)，用于在同一 NebulaGraph 实例中把独立源空间 A 搬到独立目标空间 B。它也适用于两套可分别访问的集群：先在源环境保存搬迁文件和 FETCH 基准，再把文件复制到目标环境导入、采集和离线比较。

每个场景的精确名称、Schema、代表值、每种代表值出现次数、预期数量、六条抽样查询，都在 [ngql/scenarios.json](ngql/scenarios.json) 中。场景列表见 [SCENARIO_MATRIX.md](SCENARIO_MATRIX.md)，生成器说明见 [README-FIXTURES.md](README-FIXTURES.md)。最终实际结果见 [任务产出报告](../任务产出报告.md)，不可把本指导书中的预期值当作已经通过的结果。

## 1. 验收口径

一个正常场景必须同时满足以下条件，才算通过：

1. nebula-console 执行预制数据没有 nGQL 错误。每个场景至少有 1,000 个不同 VID 的点及 1,000 条不同完整键的边。
2. 源数据核对器逐条核对所有预制记录的原生字段、完整键和 Schema，确认代表值实际写入；源端新提交的统计任务成功完成，SHOW STATS 与夹具预期的点数、边数以及每个 Tag/Edge 的记录数完全一致。
3. scan 导出的校验计划包含预期的全部点、边 ID；源 FETCH 基准在目标导入开始前完成，状态为 COMPLETE。
4. 新目标导入完成后，搬迁工具自身的逐键、逐属性精确比较通过。
5. 独立 verification JAR 对同一计划在目标执行 FETCH；离线比较结果为 MATCH。不能只比较 console 显示文本来证明二进制属性相同。
6. 目标重新统计的结果同时等于源端统计和夹具预期；六条固定 FETCH 抽样查询的结果表一致。

非法输入场景另有 1,000 个有效点及 1,000 条有效边作为对照，先保存对照内容，再执行 1,000 次应被拒绝的请求。要求拒绝次数准确，对照数据的内容、数量未改变，随后对照数据也必须完成上述搬迁和校验全流程。

每个场景的 1,000 条记录循环分配给一组代表值。例如一个类型有 7 个边界代表值，是这组场景共有 1,000 条记录，并非每个边界值各有 1,000 条。有限样本不能枚举无限字符串或所有浮点位模式。

## 2. 类型及场景分组

| 分组 | 关注点 | 比较方式 |
|---|---|---|
| VID | FIXED_STRING(256) 与 INT64；整数上下界、空 VID、字节长度边界、非零单字节、无效 UTF-8、特殊字符 | 完整字节或有符号 64 位整数键；计划 ID 数量与统计双重检查 |
| BOOL、INT8/16/32/64 | 真假、上下界、相邻值、零、超过浮点精确整数范围的数 | 原生类型及整数值 |
| FLOAT、DOUBLE | 最大有限值、最小正规/次正规值、相邻值、负零、服务端允许的非有限值 | 源原生读出后的 IEEE 754 位模式；FLOAT 先由源存储舍入 |
| STRING | NULL、空串、字面 NULL、引号、反斜杠、CR/LF、NUL、全 256 字节、emoji、组合字符、无效 UTF-8、64 KiB 长值 | 原始字节；不进行 UTF-8 修复或 Unicode 规范化 |
| FIXED_STRING | 空串、容量边界、特殊字符 | 源返回的字节；业务内容含 NUL 不在本任务的源数据前提内 |
| DATE、TIME、DATETIME、TIMESTAMP | 负年及年份边界、闰日、午夜、微秒、纪元及高时间戳 | 原生年月日、时分秒微秒或整数时间戳，不经本机时区转换 |
| DURATION | 月、秒、微秒分量及符号、边界 | 分量值，不把月份折算为天数 |
| GEOGRAPHY | POINT、LINESTRING、POLYGON、内环、日期线、极值、高精度、混合形状及 Schema 形状约束 | 形状、坐标原始位模式、点顺序及环顺序；以源服务端首次写入后读出的规范化值为准 |
| 图结构与 Schema | 零属性、多 Tag、孤立点、自环、平行边、rank 边界、中文和需引用名称、NOT NULL、DEFAULT | Tag 集合、完整边键、属性及 Schema |
| 分页 | 7 个分区，limit=1/7/127/1000/1001 | 每种 limit 都重扫源和目标，与已保存搬迁文件的全部记录比较 |
| 拒绝与损坏检测 | 越界输入、服务端不接受的 rank、非法地理值、内容或证据文件被修改 | 明确检出差异或错误，不能输出 MATCH |

持久化属性共 15 类：BOOL、INT8、INT16、INT32、INT64、FLOAT、DOUBLE、STRING、FIXED_STRING、DATE、TIME、DATETIME、TIMESTAMP、DURATION、GEOGRAPHY。列表、集合、映射、路径等查询结果结构不是该版本可声明的持久化属性类型，不作为额外 Schema 类型。

## 3. 环境准备

本次验证环境的数据库目录为 `/home/sch/nebula-run/nebula-3.6`，console 为 `/home/sch/nebula-run/nebula-console`，Graph/Meta 端口为 9669/9559。需要 Python 3、Java 8 或以上运行环境，以及构建时使用的 Maven。示例均在工程根目录执行。

```bash
cd /home/sch/nebula/nebula-java
/home/sch/nebula-run/nebula-3.6/scripts/nebula.service status graphd
/home/sch/nebula-run/nebula-3.6/scripts/nebula.service status metad
/home/sch/nebula-run/nebula-3.6/scripts/nebula.service status storaged
export NEBULA_PASSWORD=nebula
```

如果对应服务未运行，使用相同脚本的 `start` 参数启动。测试期间保持源数据和 Schema 不变，禁止同时向源空间写业务数据。目标空间必须不存在；每次独立重复验收使用新前缀。不要为了重跑而删除已有业务空间。

console 需要支持八进制字符串转义；先验证下面结果为 1。STRING 中的全部字节由三位八进制转义表达，NGQL 文件本身不会含裸 NUL 或无效 UTF-8。

```ngql
YIELD size("\000") AS byte_count;
```

## 5. 手工执行一个正常场景

以 STRING 特殊字符的字符串 VID 场景 `string_special_s` 为例，原始交付文件使用 `qa_20260914_s_string_special`，目标名为其后加 `_target`。如已有同名空间，应先按上一节生成新前缀，再从新元数据读取名称。

```bash
/home/sch/nebula-run/nebula-console -addr 127.0.0.1 -port 9669 -u root -p "$NEBULA_PASSWORD" -f task/acceptance/ngql/string_special_s/space.ngql
```

等待至少 20 秒，让 Schema 传播，然后执行 `schema.ngql`，再等待至少 20 秒，最后执行 `data.ngql`。其他场景完全相同。服务端心跳配置不同的环境应使用足够的传播等待时间。

console 的进程退出码不能独立代表成功。必须检查所有输出，不得含 `[ERROR (`；预期拒绝场景除外。

还需要验证“预制表达式 → 源实际存储”本身正确，而不只是验证“源与目标相同”。执行 `bash task/acceptance/build.sh` 后，用下列命令生成并运行源数据核对器：

```bash
python3 task/acceptance/generate_source_oracles.py \
  --fixtures task/acceptance/ngql --out task/acceptance/oracles
java -cp verification/target/nebula-data-verifier-3.8.4.jar:verification/target/fixture-oracle \
  FixtureSourceOracle --oracle task/acceptance/oracles/string_special_s.json \
  --space qa_20260914_s_string_special --out /tmp/manual-string-source-oracle.json
```

新前缀夹具应使用其对应路径生成独立 oracle，不能借用另一套夹具的文件。核对器通过源端 YIELD 计算预制表达式的原生值，再逐个 FETCH 核对所有 1,000 点、1,000 边的完整字段；FLOAT 明确按存储类型舍入为 float32 后提升，GEOGRAPHY 直接使用服务端已规范化的原生表达式结果，不对 FETCH 结果做额外近似或拓扑归一化。结果必须为 `PASSED`，核对行数为 2,000。这样可以检出“边界表达式写入成了错误的 NULL，但两端都一样”的假通过。

执行源端统计：

```ngql
USE qa_20260914_s_string_special;
SUBMIT JOB STATS;
```

记下本次返回的任务 ID，执行 `SHOW JOB <id>;`，直到任务 `FINISHED` 且任务明细成功，然后再执行 `SHOW STATS;`。这个场景应为 `case_tag=1000`、`case_edge=1000`、`vertices=1000`、`edges=1000`。多 Tag 场景额外有 `extra_tag=1000`，但空间点数仍为 1000。[官方统计说明](https://docs.nebula-graph.io/3.6.0/3.ngql-guide/7.general-query-statements/6.show/14.show-stats/)

导出文件并在导入之前保存源 FETCH 基准：

```bash
java -jar migration/target/migration-3.8.4.jar export \
  --source-space qa_20260914_s_string_special --directory /tmp/manual-string-bundle \
  --source-host 127.0.0.1 --source-graph-port 9669 --source-meta-port 9559 --scan-limit 113
java -jar verification/target/nebula-data-verifier-3.8.4.jar prepare \
  --migration-dir /tmp/manual-string-bundle --out /tmp/manual-string-plan
java -jar verification/target/nebula-data-verifier-3.8.4.jar capture \
  --plan /tmp/manual-string-plan --space qa_20260914_s_string_special \
  --host 127.0.0.1 --port 9669 --out /tmp/manual-string-source
```

检查计划 `plan.json` 中 `vertexCount=1000`、`edgeCount=1000`；源快照 `manifest.json` 的状态为 `COMPLETE`，`missingCount`、`errorCount` 均为 0。

```bash
java -jar migration/target/migration-3.8.4.jar import \
  --directory /tmp/manual-string-bundle --target-space qa_20260914_s_string_special_target \
  --target-host 127.0.0.1 --target-graph-port 9669 --target-meta-port 9559 \
  --schema-wait-ms 20000 --scan-limit 113
java -jar verification/target/nebula-data-verifier-3.8.4.jar capture \
  --plan /tmp/manual-string-plan --space qa_20260914_s_string_special_target \
  --host 127.0.0.1 --port 9669 --out /tmp/manual-string-target
java -jar verification/target/nebula-data-verifier-3.8.4.jar compare \
  --source /tmp/manual-string-source --target /tmp/manual-string-target \
  --out /tmp/manual-string-comparison
```

要求两个 JAR 的命令退出码均为 0；独立报告 `comparison-report.json` 为 `MATCH`，`matched=true`。重新提交目标统计任务，再按同样步骤与源端及夹具数量比较。

`sample.ngql` 提供第 0、500、999 条点和边的六条 FETCH 查询，都带必需的 YIELD。执行源抽样后，将文件中的 USE 空间名改为目标名，保持查询内容相同后执行。比较结果表，排除提示符中的空间名、执行时间和日期。console 会格式化二进制及浮点显示，所以该检查是补充，完整原生内容一致仍以 verification 结果为准。

## 6. 非法输入场景的手工顺序

按 `space.ngql → 等待 → schema.ngql → 等待 → control.ngql` 建立有效对照。先通过 verification 保存对照快照，再执行 `data.ngql`。这个文件中的 1,000 个请求应全部失败；不能误把它当作正常数据文件要求无错误。

要求 1,000 条拒绝错误与该场景的拒绝原因相符，再对同一计划采集源端新快照并离线比较，对照应完全不变。重新统计结果仍为 1,000 点、1,000 边。随后按上一节将有效对照搬到目标，完成正常场景的三路验证。

FLOAT 的正负 Infinity 表达式能计算不代表可存储。此次 3.6 环境会拒绝 FLOAT Infinity，因此它属于拒绝场景；DOUBLE 的存储行为独立测试。NaN 以服务端实际读出的规范 NaN 为准，不能据此承诺保留任意私有 NaN payload。

## 7. 批量执行与证据

串行运行器自动执行上述流程。新夹具、新源空间可直接运行：

```bash
python3 task/acceptance/run_campaign.py \
  --fixtures /tmp/nebula-manual-fixtures \
  --oracle-dir /tmp/nebula-manual-oracles \
  --work /tmp/nebula-manual-work \
  --reports task/acceptance/reports/manual-run \
  --archives task/acceptance/artifacts/manual-run
```

上例需先执行 `python3 task/acceptance/generate_source_oracles.py --fixtures /tmp/nebula-manual-fixtures --out /tmp/nebula-manual-oracles`。使用 `--only string_special_s,string_special_i` 可只执行指定场景。`--seed-only` 可分阶段批量创建正常源数据和负向有效对照，成功后用相同夹具加 `--already-seeded` 开始搬迁验收；1,000 次拒绝请求在验收阶段执行。`--already-seeded` 是明确使用已构造稳定源数据，不是搬迁工具的断点重试功能。复用已验证的稳定源空间完整复测时，可以用 `--target-suffix _newrun` 为全部目标增加新后缀，同时指定新的 work、reports、archives 目录；不修改原始夹具或历史结果。

每个报告记录源基准完成时间、目标导入开始时间、全部步骤与退出码、源目标统计及其期望、独立 FETCH 报告、console 抽样摘要、代表值出现次数、完整证据归档路径及 SHA-256。原始查询、输出、CSV、计划和双方快照位于对应 `.tar.gz` 内。可用以下方式解包审计：

```bash
mkdir -p /tmp/nebula-case-review
tar -xzf task/acceptance/artifacts/string_special_s.tar.gz -C /tmp/nebula-case-review
```

运行器不覆盖旧输出目录，失败即停止。修复代码后使用新的输出位置与未使用过的目标空间重新验收，保留失败证据。最终产出报告同时记录发现的问题、修复和复测结果。

## 8. 适用范围

新导出包包含完整的原生 Schema。导入工具先通过 Graph 认证创建目标空间，再连接目标 Meta 服务重建 Tag/Edge，保留默认表达式的编码字节、列和表注释；空间注释由原始字节重建。因此目标 Meta 端口必须可达。默认表达式的内部编码要求源与目标服务端版本及平台兼容，本次真实验证为同一套本地 3.6 服务。包含 DEFAULT 的旧导出包需要重新导出，不能依赖 `SHOW CREATE` 的展示文本恢复复杂默认值。

默认值和注释另有两组补充压力用例，执行说明见 [schema-probes/README.md](schema-probes/README.md)。其中随机和时间默认函数在源首次 INSERT 时计算，搬迁传递已存储的值；另行核对目标 Schema 保留原始动态表达式，不能把重新执行随机函数所得值当成源记录的预期值。这两组使用专门的 Schema/default 核对器，主场景的完整源数据核对仍是必需门禁。

本验收面向固定版本和配置下的静止源数据，目标为独立新空间。索引、用户权限、集群运维配置、在线业务并发一致性不在内容搬迁范围内。当前工具在内存中保存完整数据用于精确比较；64 KiB 场景是实际长度测试，不是无限字符串长度或任意规模内存占用的保证。

GEOGRAPHY 的坐标以源端原生查询返回值为基准。合法几何写入时可能发生服务端归一化，不能把原始 WKT 文本与其规范化结果的差异归为搬迁丢失。[官方 GEOGRAPHY 说明](https://docs.nebula-graph.io/3.6.0/3.ngql-guide/3.data-types/10.geography/)

VID 或 FIXED_STRING 业务内容含 NUL、无 Tag 点以及活动 TTL 等既有接口前提仍须满足。任务增加 GEOGRAPHY 支持不等于解除这些独立边界。通过本测试矩阵说明列出的场景已验证，不能替代目标商业环境的版本、规模和业务验收。
