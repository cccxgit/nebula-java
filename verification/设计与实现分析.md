# 独立校验工具：设计与实现分析

本模块对**同一份固定 ID 清单中的点、边，在源端和目标端分别读取到的完整内容**进行比较。`MATCH` 表示两次采集均完整且这些对象一致；它不表示清单覆盖全库，也不证明两次采集对应同一个数据库事务时刻。

日常执行命令、文件示例和退出码见 [使用说明](README.md)。本文说明代码如何得到结论，以及结论的适用范围。

## 1. 独立校验 JAR 的结构

构建产物为 `nebula-data-verifier-3.8.4.jar`，运行时包含客户端及其依赖，只需要连接 graphd。`prepare`、`prepare-ids` 和 `compare` 都不访问数据库；`capture` 只读数据库，每次只连接一个集群。源、目标因此可以分别采集，再把文件汇总到一台机器比较。

| 组件 | 责任 |
|---|---|
| [VerifierCli](src/main/java/com/vesoft/nebula/verification/VerifierCli.java) | 参数校验、四个子命令分发、报告输出与退出码 |
| [PlanBundle](src/main/java/com/vesoft/nebula/verification/PlanBundle.java) | 固定点边清单、去重规则、计划身份和键文件摘要 |
| [FetchCollector](src/main/java/com/vesoft/nebula/verification/FetchCollector.java) | 逐对象 FETCH、核对返回标识及 Schema、记录采集状态 |
| [Identifiers](src/main/java/com/vesoft/nebula/verification/Identifiers.java) | 清单标识编解码、原始字节 VID 查询表达式、Schema 名称引用 |
| [NativeValueCodec](src/main/java/com/vesoft/nebula/verification/NativeValueCodec.java) | 独立的原生值编码、完整点边字段展开 |
| [SnapshotFiles](src/main/java/com/vesoft/nebula/verification/SnapshotFiles.java) | 写入和读取快照，检查摘要、覆盖数量、重复记录和完成状态 |
| [OfflineComparator](src/main/java/com/vesoft/nebula/verification/OfflineComparator.java) | 离线核对相同清单的字段及相关 Schema，生成差异报告 |

校验模块不依赖 `migration` 模块，也不复用其 `ValueCodec`。搬迁通过 Storage scan 导出，校验通过 Graph FETCH 回读，并使用另一套原生值编码。这样可以发现搬迁链路的编码、标识或字段遗漏错误。两者仍使用同一 nebula-java 客户端，校验对象也仍是服务端接口可读的值，不能据此恢复接口已经丢失的信息。

## 2. 四个命令的调用链

### prepare：从搬迁导出文件提取清单

`VerifierCli → PlanBundle.prepare → write`

读取搬迁 `manifest.json`，核对格式版本、编码规则、表清单、CSV 文件名、SHA-256、表头、列数、行数及标识。只提取 ID，不把搬迁 CSV 属性值作为正确答案。

- 同一 Tag 内重复 VID、同一 Edge 表内重复完整边键会被拒绝。
- 同一 VID 出现在不同 Tag 文件中是正常的，汇总为一个点请求。
- 边使用名称、起点、rank、终点组成逻辑键；起点和终点也加入点清单。
- 输出 `plan.json`、`vertices.csv`、`edges.csv`，记录计划 ID、VID 类型、清单数量和键文件摘要；同时记录输入搬迁 manifest 的摘要。

它验证的是导出文件中清单的结构和完整性。若导出阶段漏掉整个点或边，且相关文件及 manifest 本身一致，本命令无法发现“本应存在但未列入”的对象。

### prepare-ids：从独立 ID CSV 创建清单

`VerifierCli → PlanBundle.prepareIds → readIds → write`

点文件表头为 `vid`，边文件为 `src,edge,rank,dst`；键单元格使用带必要填充的标准 `V:Base64`。两个文件都必须存在，没有对应对象时只保留表头；整个清单不能为空。

此入口拒绝重复标识，并按调用方明确给出的点清单查询点，**不自动把边端点加入点清单**。如果还要核对边端点的 Tag 和属性，调用方应将端点加入点 CSV。

两个入口都会生成新的计划 ID。源、目标必须复制并使用同一个完整 plan 目录，不能分别运行 `prepare` 后再尝试比较。

### capture：采集一个图空间

`VerifierCli → PlanBundle.load → FetchCollector.capture → SnapshotFiles.finish`

先验证 plan 文件摘要，检查空间 VID 类型与清单一致。字符串 VID 查询前，用 255 个非 NUL 字节做一次只读八进制转义探测，确认服务端能逐字节恢复查询字面量。

采集器读取初始 Schema，再逐条执行以下形态的 nGQL：

```ngql
FETCH PROP ON * <VID表达式> YIELD vertex AS v;
FETCH PROP ON `<Edge名称>` <SRC表达式>-><DST表达式>@<rank> YIELD edge AS e;
```

每个请求都产生一个结果记录：

- `OK`：返回原生对象、身份符合请求、属性集合及类型通过校验。
- `MISSING`：没有对应对象；点返回空 Tag 集合也按缺失处理。
- `ERROR`：查询失败、返回类型或身份错误、Schema/字段不完整、出现不支持的值等。

采集结束后，重新读取实际涉及的 Schema 与空间 VID 类型，发现变化或复查失败就标记采集不完整。连接或初始化阶段直接失败可能不生成有效快照；不会以空目录或没有 manifest 的文件集表示成功。

### compare：离线得出结果

`VerifierCli → OfflineComparator.compare → SnapshotFiles.load（两端）`

读取并校验两份快照，要求计划 ID、计划摘要、VID 类型和实际请求键集合一致，再按键比较 Schema 和字段。空间名称、采集时间、记录顺序不参与内容相等判断。

| 结果 | 判断条件 | 退出码 |
|---|---|---:|
| `MATCH` | 两端均完整，相关 Schema 和全部清单对象字段相同 | 0 |
| `DIFFERENT` | 两端均完整，存在内容或相关 Schema 差异 | 2 |
| `ERROR` | 采集不完整、对象缺失、查询失败、文件损坏或批次不匹配 | 1 |

## 3. 值、真实 Tag 和边身份如何保留

### 值采用带类型的原生编码

`NativeValueCodec` 将标量编码为确定性的 ASCII JSON 数组；外层 `records.jsonl` 再将它保存为字符串。字符串中的引号、换行、NUL 或无效 UTF-8 不会改变文件的记录边界。

| 原生内容 | 内层载荷示例 | 完整性要点 |
|---|---|---|
| 正常 NULL | `["null"]` | 与空字符串区别；错误 NULL 不可转为正常 NULL |
| 空字符串 | `["string",""]` | 保留长度为零的字节数组 |
| `abc<NUL>def` | `["string","YWJjAGRlZg=="]` | 直接编码 `sVal` 字节，不先转 Java String |
| INT64 最大值 | `["int","9223372036854775807"]` | 十进制字符串，不经过 double |
| 浮点负零 | `["float","8000000000000000"]` | 比较返回 double 的 raw64 位，不使用误差阈值 |
| TIME 微秒 | `["time","13","14","15","123456"]` | 保留原字段，不经过时区或展示格式转换 |
| DURATION | `["duration","2","259204","500006"]` | 按月份、秒、微秒分别保留，不折算月份或归一化 |

FLOAT 读出的值已经提升为 double，编码保留这个返回值的位模式；FLOAT 与 DOUBLE 的 Schema 类型另行比较。INT8/16/32/64、TIMESTAMP 同理：原生整数值和准确 Schema 类型共同确定含义。

编码层能表示 `fVal` 中的 NaN、Infinity 和不同 NaN 位模式，但这不证明数据库可以写入任意这种值。协议中的 `NullType.NaN` 属于异常 NULL，会被拒绝。GEOGRAPHY 及其他不支持的原生类型也不会被忽略。

### 点核对完整的实际 Tag 集合

点使用 `FETCH PROP ON * ... YIELD vertex` 返回的实际 Tag 集合，展开为：

```text
$vid
tag/<Tag名称Base64>                         = present
tag/<Tag名称Base64>/prop/<属性名称Base64>    = 原生值编码
```

无属性 Tag 仍有 `present` 标记，所以“没有这个 Tag”和“有这个 Tag，但没有属性”可区分。每个实际 Tag 的属性名称集合必须与 Schema 完全一致，不能把少返回一个可空属性当成该属性为 NULL。

Tag/属性名称按原始字节编码，字段按键排序；同名的不同 `byte[]` 对象仍会被识别为重复。标记识别使用 `present` 值，不把 Base64 名称中的 `/` 误认为属性路径。

### 边核对完整逻辑键

边展开为 `$src`、`$dst`、`$name`、`$rank` 和全部 `prop/<名称Base64>` 字段。内部数字 `edge.type` 不参与比较，因为不同空间独立建 Schema 后数字 ID 可能不同；返回的 Edge 名称必须与请求相同。

字符串 VID 保留原始字节，查询字面量的每个字节使用固定三位八进制转义。INT64 VID 最小值使用 `toInteger("-9223372036854775808")` 表达。当前 nGQL rank 语法无法表示 INT64 最小值，工具明确拒绝该 rank，不截断或替换。

## 4. Schema、快照完整性和错误处理

相关 Schema 比较包含**属性名称、准确类型、可空性**。点以 FETCH 实际返回的 Tag 为准；边以清单中的 Edge 名称为准。默认表达式、注释、索引、TTL 配置和无关 Schema 不参与比较。列顺序通过按属性名称排序消除，未使用内部 Tag/Edge 数字 ID。

快照记录每个请求的结果，manifest 保存计划身份、请求键摘要、记录文件 SHA-256、请求/实际记录数量、成功/缺失/错误数量和完成状态。[SnapshotFiles](src/main/java/com/vesoft/nebula/verification/SnapshotFiles.java) 在写完和重新加载时都检查这些约束：

- 重复记录、缺物理记录、空行、字段缺失或计数矛盾被拒绝。
- `COMPLETE` 要求没有 `MISSING`、`ERROR` 或采集级错误。
- 两侧恰好发生相同错误，比较结果仍为 `ERROR`，不能得到 `MATCH`。
- 输出目录必须为空，未结束的写入不能冒充有效快照。

摘要用于检测文件损坏和防止混用批次；当前没有数字签名机制。应完整传递原 plan 与快照目录，不手工修改 manifest 来绕过检查。

报告最多保存 1,000 条差异明细，单个长值预览最多 256 个字符；差异计数和最终结论不会因展示截断而改变。完整编码值保留在两侧 `records.jsonl` 中。

## 5. 数据稳定前提和性能边界

正确的使用时序是：

1. 从源数据导出开始前，保持源空间数据、Schema 和 TTL 过期行为稳定。
2. 完成搬迁数据导出，生成 plan，并完成源端 FETCH 基准采集。
3. 源端基准和导出完成后，再允许源端继续变化；迁移到目标的是这批已固定的导出数据。
4. 等待目标导入结束，目标在 FETCH 采集期间保持稳定，再比较两份快照。

一次 `capture` 内是多次独立查询，**没有跨对象的一致性快照或事务**。前后 Schema 复查只能发现观察到的定义变化，不能发现所有“变更后又恢复”的情况，也不能发现所有并发属性更新。比较结果描述历史采集内容，不代表执行 `compare` 时源库的实时状态。

本版本按正确性优先实现：单连接、逐对象查询，不提供高并发、批量性能优化、自动重试或断点续采。plan 的 ID 集合保存在内存；采集虽然逐行写文件，结束校验会重新加载全部记录；离线比较也会将两侧完整记录载入内存。大规模使用需要按数据体积安排堆内存和磁盘，不能把“逐行写文件”理解为恒定内存。单条数据还受服务端/RPC 限制。

## 6. 已验收内容与尚未完成的边界

已有证据见 [2026-09-13 验收记录](acceptance/2026-09-13/README.md) 和 [单元测试汇总](acceptance/2026-09-13/unit-test-summary.json)：

- 在同一台 NebulaGraph 3.6 实例、client 3.8.4 上，字符串 VID 和 INT64 VID 两组分别核对 127 个点、131 条边，共 516 个清单对象；初始和恢复后均为 `MATCH`。
- 样本包含全部已支持属性类型、NULL/空串、整数边界、有限浮点极值/非正规数/负零、微秒、DURATION 边界，以及全部 256 种字节、无效 UTF-8、组合字符和约 1 MiB 字符串。
- 真实修改目标后，单个浮点位变化、缺少/增加无属性 Tag 被判为 `DIFFERENT`；缺少无属性边被判为 `ERROR`；不存在的空间拒绝采集。修改恢复后重新匹配。
- 78 项校验单元测试及 18 项客户端扫描回归通过。最终独立 JAR 的 `prepare/capture/compare` 命令分别作为进程运行，核对了 0、2、1 三种退出码；离线命令没有数据库密码或连接参数。

这些验收没有覆盖实际异地网络、不同部署拓扑、不同服务端版本的双集群搬迁，也没有证明严格执行“先源基准采集、再向全新目标导入”的完整生产时序；正式验收使用的是已经导入并稳定的测试目标。当前也未完成跨查询一致性快照、在线写入/TTL 变化下的一致性保证或大规模性能验收。

独立校验 JAR 可按既有设计复制到不同环境分别采集，但实际异地运行仍需在对应环境验收。对全库迁移的完整性，应另行确保清单覆盖了应搬迁的所有对象；本模块不会查询清单之外的额外点或边。
