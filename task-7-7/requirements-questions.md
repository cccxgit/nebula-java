# Nebula Graph 跨集群搬迁需求澄清问题

## 当前理解

当前需求是：面向生产环境实现 Nebula Graph 跨集群搬迁能力。源集群和目标集群的 graph、meta、storage 服务均采用 3 实例分布式部署。技术选型限定为 Java 和 Shell，第三方件限定为 nebula-java，不考虑 Spark、Flink、Nebula Importer 等其他组件。

核心链路初步理解为：

1. 使用 nebula-java 直连源集群 storage 服务导出数据。
2. 将导出数据保存为 CSV 或 JSON 文件。
3. 使用 nebula-java 将文件数据导入目标集群。

## 1. 搬迁模式

1. 这是一次性全量迁移，还是需要支持“全量 + 增量追平 + 最终切换”？
2. 源集群在导出期间是否继续写入？
3. 是否允许业务停写窗口？如果允许，大概是分钟级、小时级，还是越短越好？
4. 目标集群是否必须在迁移完成后与源集群完全一致，还是允许最终一致并通过校验发现差异？

## 2. 数据范围

5. 迁移对象是整个 Nebula 集群，还是指定 space？
6. 是否需要迁移 schema，包括 space、tag、edge、index、TTL、全文索引、配置项等？
7. 是否需要迁移用户、角色、权限？
8. 是否需要迁移作业状态、统计信息、balance 状态、compact 状态这类系统元信息？

## 3. 导出/导入路径

9. “nebula-java 直连 storage 导出”具体期望使用 StorageClient scan vertex/edge 这类接口，对吗？
10. 目标集群导入是通过 graph service 执行 `INSERT VERTEX/EDGE`，还是也希望绕过 graph 直写 storage？
11. CSV/JSON 文件只是中间格式，还是需要作为可审计、可长期保存的交付物？
12. 文件格式更偏向性能优先的 CSV，还是可读性/兼容性优先的 JSON？

## 4. 一致性和快照

13. 导出时是否要求一个一致性快照？比如同一批 vertex/edge 不能混入不同时间点的数据。
14. 是否可以接受按 partition/tag/edge 分片扫描时的弱一致结果？
15. 如果源集群持续写入，是否有可用的业务时间戳、版本字段或 binlog/WAL 机制用于增量追平？

## 5. 数据规模和性能目标

16. 典型数据规模是多少：点数、边数、属性总量、单 space 大小？
17. 最大规模预期是多少？
18. 期望迁移速度或完成时间是多少？例如 1TB 在几小时内完成。
19. 单机可用资源大概是多少：CPU、内存、磁盘、网络带宽？
20. 是否要求支持多进程/多机器并行导出导入？

## 6. 可靠性

21. 任务中断后是否必须支持断点续传、续导、续导入？
22. 导入是否要求幂等？重复执行不能产生重复边或错误覆盖？
23. 失败记录需要落盘并可重试吗？
24. 是否需要任务级状态管理，比如 manifest、checkpoint、进度、错误汇总？

## 7. 校验和验收

25. 迁移完成后验收标准是什么？数量一致、抽样一致、全量 checksum，还是业务查询验证？
26. 是否需要按 space、tag、edge、partition 输出校验报告？
27. 对浮点、时间、NULL、空字符串、复杂转义字符等类型是否要求字节级一致？

## 8. 版本和兼容性

28. 源集群和目标集群的 Nebula Graph 版本分别是多少？
29. 是否需要支持跨版本迁移，比如 3.5 到 3.8？
30. VID 类型是固定字符串、整数，还是两者都要支持？

## 优先确认问题

建议优先确认以下 8 个问题，确定后再继续细化设计：

1. 迁移模式：一次性全量，还是全量 + 增量追平？
2. 源集群导出期间是否继续写入？
3. 迁移范围：整个集群，还是指定 space？
4. 导出路径：是否确认使用 nebula-java StorageClient scan vertex/edge 接口？
5. 导入路径：通过 graph service 执行 `INSERT VERTEX/EDGE`，还是直写 storage？
6. 一致性要求：是否要求一致性快照？
7. 数据规模：典型和最大点边规模、数据容量是多少？
8. 验收标准：数量一致、抽样一致、checksum，还是业务查询验证？
