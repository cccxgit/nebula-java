# 2026-07-08 第四轮需求确认与剩余 GAP

## 1. 本轮新增确认

### 1.1 文件布局开发范围

已确认：

1. `label` 布局需要参数设计和代码开发。
2. `partition` 布局需要参数设计和代码开发。
3. `segment` 布局仅输出设计文档，本需求不开发代码实现。

建议参数：

```text
export.file.layout = label | partition
```

说明：

1. 默认值为 `label`。
2. `segment` 在设计文档中作为未来扩展，不作为本期可执行参数。

### 1.2 TTL 标记位置

已确认：

1. TTL 标记写入 `manifest.json`。
2. TTL 标记写入导出报告或迁移报告。
3. TTL 标记不写入 CSV/JSON 数据正文。

### 1.3 HMAC 签名密钥

已确认：

1. HMAC 签名密钥采用默认值。
2. 用户无需自行提供。

需要在设计文档中明确：

1. 默认 HMAC 主要用于标记文件完成和防止误用未完成文件。
2. 如果默认密钥是固定内置值，则签名不具备强安全防篡改能力。
3. 完整性校验仍以 `SHA-256` 为主。

### 1.4 目标集群初始用户

已确认：

1. 目标集群初始状态要求仅存在 `root` 用户。
2. `root` 用户不做处理。
3. 如果目标集群存在除 `root` 外的用户，则 precheck 失败并停止导入。

### 1.5 schema/index 创建失败恢复

已确认：

1. schema/index 创建失败后，要求清理目标集群再重试。
2. 本期不做 schema/index 阶段的复杂断点续导。

## 2. 当前仍需确认的 GAP

### 2.1 默认 HMAC 密钥的准确语义

当前确认“采用默认 HMAC 密钥，无需用户提供”。这里需要明确默认密钥来源。

候选方案：

1. 固定内置默认密钥。
2. 每次导出任务自动生成随机密钥，并写入导出目录中的受控 metadata。
3. 从配置文件读取，如果未配置则使用内置默认值。

建议：

```text
固定内置默认密钥。
```

理由：

1. 符合“无需自行提供”。
2. 实现简单。
3. 当前签名主要作为“文件已完整导出”的完成标记，而不是安全认证机制。

需要在设计文档中明确风险：

```text
默认 HMAC 不作为安全防篡改承诺；如果需要安全防篡改，需要后续增强为用户自定义密钥或非对称签名。
```

### 2.2 label 布局的并发导出写入方式

`label` 布局是一个 tag/edge 一个大文件，但导出又要求支持多 storage、分片级并发扫描。

需要确认 label 布局下如何写单文件。

候选方案：

1. 多 partition 并发 scan，单 writer 串行写入同一个 tag/edge 文件。
2. 每个 partition 先写临时片段文件，tag/edge 完成后 merge 成一个大文件。
3. label 布局下关闭 partition 并发，按 partition 顺序扫描并写入单文件。

建议：

```text
多 partition 并发 scan，单 writer 串行写入同一个 tag/edge 文件。
```

理由：

1. 保留并发读取能力。
2. 避免多个线程同时写同一文件造成数据交错。
3. 不引入额外 merge 阶段。

但需要接受：

1. 文件行顺序不作为一致性标准。
2. label 文件无签名时整体重导。
3. label 布局 checkpoint 粒度是 tag/edge 文件级，不是 partition 级。

### 2.3 partition 布局的恢复粒度

需要确认 partition 布局的恢复语义。

建议：

1. 每个 `space + tag/edge + partition` 一个文件。
2. 每个 partition 文件独立生成 `sha256` 和 `sig`。
3. 恢复时已签名 partition 文件跳过。
4. 未签名 partition 文件整体重导。

### 2.4 CSV 编码细节

已确认默认 CSV，同时支持 JSON，但 CSV 需要定义可逆编码规则。

建议：

1. 使用 RFC4180 风格 CSV。
2. 逗号、双引号、换行字段使用双引号包裹。
3. 字段内双引号写作两个双引号。
4. `NULL` 使用保留标记，例如 `\N`。
5. 空字符串写作空 quoted 字段：`""`。
6. 普通字符串 `\N` 需要按字符串转义或通过 schema type 识别避免与 NULL 混淆。
7. 列类型、列顺序、VID 类型写入 schema metadata，不只依赖 CSV header。

需要确认：

1. `NULL` 是否接受使用 `\N` 表示？
2. 空字符串是否接受使用 `""` 表示？

### 2.5 JSON 编码细节

建议 JSON 使用 typed JSON，避免类型歧义。

示例：

```json
{
  "vid": {"type": "string", "value": "player100"},
  "props": {
    "name": {"type": "string", "value": "Tim Duncan"},
    "age": {"type": "int", "value": 42},
    "memo": {"type": "null", "value": null}
  }
}
```

需要确认是否接受 typed JSON，而不是普通扁平 JSON。

### 2.6 导入批量失败重试策略

需要确认导入阶段失败处理。

建议：

1. 批量 `INSERT` 失败后，按单行降级重试。
2. 单行失败后写入失败记录文件。
3. 失败记录包含：
   - 原始文件路径
   - 行号
   - vertex/edge key
   - 原始行文本
   - 生成的 nGQL
   - 错误码
   - 错误消息
   - 重试次数

### 2.7 导入幂等语义

需要确认：

1. 重复导入同一份导出文件时，允许同 key 同值覆盖。
2. 因目标集群 precheck 要求无业务数据，不处理“同 key 不同值”的业务冲突。
3. 如果导入中断后恢复，已成功导入的数据再次执行 `INSERT` 可以接受。

建议接受上述语义。

### 2.8 清理目标集群的执行责任

已确认 schema/index 创建失败后要求清理目标集群再重试。

需要确认：

1. 清理目标集群由工具自动执行，还是由用户手动执行？
2. 如果自动执行，是否允许工具执行 `DROP SPACE`、`DROP USER` 等破坏性操作？

建议：

```text
本期由用户手动清理目标集群，工具只报错并给出清理提示，不自动执行 DROP。
```

理由：

1. 降低误删风险。
2. 符合生产工具保守策略。

### 2.9 root 用户是否从源集群导出

目标集群 `root` 不处理，但源集群可能也有 `root`。

需要确认：

1. 导出用户列表时是否跳过 `root`？
2. 导入用户时是否永远不创建、不修改、不授权 `root`？

建议：

```text
跳过 root 用户；root 不导出、不导入、不改密、不改权限。
```

### 2.10 权限迁移范围

此前确认用户、角色、权限都需要搬迁，但现在 `root` 不处理，用户密码统一默认。

仍需确认：

1. 是否迁移非 root 用户的 space 级角色授权？
2. 是否迁移商业版用户 privilege、IP whitelist、资源限制等扩展权限？
3. 如果某类权限无法通过 nebula-java 或 nGQL 完整导出，是报错、告警，还是跳过？

建议：

```text
本期迁移非 root 用户的 space 级角色授权；无法完整导出的商业版扩展权限先告警并写入报告。
```

## 3. 建议优先确认

建议优先确认以下问题：

1. 默认 HMAC 是否采用固定内置密钥，并声明不作为安全防篡改能力？
2. `label` 布局是否采用多 partition 并发 scan + 单 writer 串行写文件？
3. CSV 中 `NULL=\N`、空字符串=`""` 是否接受？
4. JSON 是否接受 typed JSON？
5. 导入批量失败后是否降级单行重试？
6. 目标集群清理是否由用户手动执行，工具不自动 DROP？
7. 是否跳过 `root` 用户的导出、导入、授权处理？
