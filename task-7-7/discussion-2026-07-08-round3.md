# 2026-07-08 第三轮需求确认与剩余 GAP

## 1. 本轮新增确认

### 1.1 导出文件布局默认值

已确认：

```text
export.file.layout = label
```

含义：

1. 默认采用一个 tag/edge 一个大文件。
2. `label` 布局下，一个 tag/edge 文件没有签名时，需要整体重新导出。
3. `segment` 布局本需求仅输出设计文档，无需开发代码实现。

当前理解：

1. 本期代码实现至少需要支持 `label` 布局。
2. 是否需要同步开发 `partition` 布局仍需确认。
3. `segment` 布局只进入设计方案和未来扩展说明，不进入本期开发和测试验收。

### 1.2 TTL 处理策略

已确认：

1. 导出阶段如果识别到模型/schema 存在 TTL，则打印告警日志。
2. 日志采用 log4j。
3. 即使存在 TTL，也继续执行导出任务。
4. 在导出结果文件中标记存在 TTL。
5. 测试阶段和生产阶段的校验策略不因存在 TTL 而变化。

当前理解：

1. TTL 只作为风险提示，不阻断导出。
2. TTL 不改变默认数量一致、抽样一致校验策略。
3. TTL 不强制开启全量 checksum。
4. TTL 标记需要进入 manifest 或导出结果报告。

### 1.3 checksum 和签名

已确认参考前述方案：

1. checksum 使用 `SHA-256`。
2. 签名建议使用 `HMAC-SHA256`。
3. 单文件完成后生成 checksum 和签名。
4. 有签名的文件恢复时可跳过。
5. 无签名文件视为未完成。

### 1.4 label 布局恢复语义

已确认：

1. `label` 布局中，一个 tag/edge 一个大文件。
2. 如果该大文件没有签名，则需要整体重导。

## 2. 当前需要继续确认的 GAP

### 2.1 本期代码实现是否支持 partition 布局

前一轮确认过支持三种方案：

1. `label`
2. `partition`
3. `segment`

本轮又确认：

1. `label` 是默认值。
2. `segment` 只输出设计文档，不开发代码实现。

仍需确认：

1. 本期代码是否需要实现 `partition` 布局？
2. 如果实现 `partition` 布局，是否作为非默认可选参数？
3. 如果不实现 `partition` 布局，本期代码是否只实现 `label`，并在设计文档中描述 `partition` 和 `segment` 作为扩展？

建议：

```text
本期代码实现 label + partition，默认 label；segment 只写设计文档。
```

理由：

1. partition 与 StorageClient scan 的 partition cursor 模型天然匹配。
2. partition 实现成本明显低于 segment。
3. 20 亿点边目标下，只有 label 布局会带来较大的失败重导成本。

### 2.2 “导出结果文件标记 TTL”的具体位置

需要确认 TTL 标记写在哪里。

候选方案：

1. 写入 `manifest.json` 的 space/tag/edge 级元数据。
2. 写入迁移报告 `export-report.json`。
3. 写入每个数据文件旁边的 metadata 文件。
4. 在 CSV/JSON 数据文件内容中增加标记。

建议：

```text
写入 manifest.json 和 export-report.json，不写入 CSV/JSON 数据正文。
```

理由：

1. 不污染数据文件格式。
2. 便于任务恢复、校验和审计。
3. 一个 tag/edge 是否有 TTL 是 schema 级属性，不是每行数据属性。

### 2.3 HMAC 签名密钥如何提供

需要确认签名密钥来源。

候选方案：

1. 启动参数直接传入密钥字符串。
2. 启动参数传入密钥文件路径。
3. 环境变量传入密钥。
4. 工具自动生成密钥并写入导出目录。

建议：

```text
启动参数传入密钥文件路径。
```

示例：

```text
export.signature.key-file=/path/to/hmac.key
```

并要求：

1. 日志不打印密钥内容。
2. manifest 只记录签名算法和 key id，不记录密钥。

### 2.4 用户搬迁与目标集群已有默认用户

此前确认：

1. 目标集群若存在用户，则停止导入并报错。
2. 密码无需导出，目标用户密码默认 `nebula`。

需要确认：

1. 目标集群默认内置用户是否允许存在？
2. “存在用户则报错”是否排除 Nebula 默认用户，例如 `root`？
3. 从源集群导出的用户是否包括 `root`？
4. 迁移后所有用户密码是否统一设置为 `nebula`，包括管理员用户？

建议：

```text
目标集群允许存在系统默认用户；业务用户存在则报错。源集群业务用户导入后统一默认密码 nebula。
```

### 2.5 schema/index 创建失败后的恢复语义

当前已确认数据文件导出失败恢复语义，但 schema/index 阶段还需要明确。

需要确认：

1. 如果目标集群 schema 创建到一半失败，再次执行导入任务是从头检查并跳过已创建 schema，还是要求清空目标集群后重试？
2. 如果 index 创建失败，是否停止整个导入？
3. 如果 schema 已存在但与导出 manifest 完全一致，是否允许继续？

建议：

```text
目标集群导入前要求为空；schema/index 阶段失败后，本期要求清理目标集群后重新导入，不做复杂 schema 级断点续导。
```

### 2.6 导入幂等和“不错误覆盖”的具体语义

此前要求导入幂等，重复执行不能产生重复边或错误覆盖。

在 Nebula 中：

1. 相同 VID + tag 重复 `INSERT VERTEX` 会覆盖同 tag 属性。
2. 相同 src/dst/rank/edge type 重复 `INSERT EDGE` 会覆盖同一条边属性。
3. 不同 rank 的边是不同边。

需要确认：

1. 如果导入重试写入完全相同数据，允许覆盖同值吗？
2. 如果目标已有同 key 但不同属性，是报错、覆盖，还是记录冲突？
3. 是否需要在导入前强制目标 space 为空来规避冲突？

建议：

```text
导入重试允许覆盖同 key 同值；目标集群 precheck 保证无业务数据，以规避不同值覆盖。
```

### 2.7 默认 label 布局下的大文件风险

默认 `label` 布局会产生一个 tag/edge 一个大文件。

需要确认：

1. 是否设置单文件大小告警阈值？
2. 超过阈值时是继续导出并告警，还是提示用户改用 `partition` 布局？
3. 是否允许文件超过 2GB、10GB、100GB？

建议：

```text
label 布局下只告警不阻断；超过阈值建议用户改用 partition。
```

默认阈值建议：

```text
export.label.large-file.warn.bytes = 10737418240
```

即 10GB。

### 2.9 CSV/JSON 数据类型编码细节

已确认按 typed value 语义一致，但导出文件格式仍需要定义。

需要确认：

1. CSV 中 `NULL` 如何表示？
2. 空字符串如何表示？
3. 字符串中的换行、逗号、引号如何转义？
4. 日期时间是否使用 Nebula 字面量格式，还是 ISO-8601？
5. JSON 中 VID、属性值是否携带类型信息？

建议：

```text
CSV 使用 RFC4180 风格转义，并用独立 metadata/schema 文件解释列类型和 NULL 表示；JSON 使用 typed JSON，显式保存 type/value。
```

### 2.10 导入批量大小和失败文件格式

需要确认：

1. 默认每批 `INSERT VERTEX/EDGE` 拼多少行？
2. 单批失败后是逐行降级重试，还是整批写入失败记录？
3. 失败记录文件保存原始行、解析后对象，还是 nGQL 语句？

建议：

```text
批量写入失败后降级到单行重试；单行仍失败则记录失败文件，失败文件包含原始行、解析后 key、错误码、错误消息。
```
