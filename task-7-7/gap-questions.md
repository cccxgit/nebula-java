# Nebula Graph 跨集群搬迁 GAP 问题

## 当前结论

根据对 `requirements-questions.md` 的答复，主链路已经基本清楚：

1. 本需求仅考虑一次全量搬迁。
2. 源集群导出期间需要实现数据静止，禁止增删改。
3. 导出使用 nebula-java `StorageClient scanVertex/scanEdge`。
4. 导入使用 nebula-java 连接 graph service，拼接并执行 `INSERT VERTEX/EDGE`。
5. 中间文件默认 CSV，同时支持 JSON，并作为可审计、可长期保存的交付物。
6. 需要支持断点续导出、续导入、失败落盘、失败重试、幂等执行、任务级状态管理。
7. 默认使用数量一致和抽样一致作为校验标准，额外提供手动开启的全量 checksum。

仍存在的主要 GAP 集中在：生产一致性语义、内核冻结边界、元数据搬迁边界、密码搬迁可行性、幂等冲突策略和校验口径。

## 弱一致解释

“按 partition/tag/edge 分片扫描时的弱一致”指的是：如果源集群还在写入，不同 partition、不同 tag、不同 edge type 的扫描发生在不同时间点，最终导出的数据可能不是同一个时间点的全局视图。

例如：

1. partition 1 扫描时某条边还不存在。
2. partition 2 扫描时相关点已经被更新。
3. tag A 扫描完后，tag B 又被修改。
4. 点和边之间可能出现时间点不一致。

当前答复要求导出前禁止写入，所以这个问题原则上可以规避。但前提是“数据静止”必须是一个真正生效的集群级 barrier，并且要处理导出前已经进入系统的 in-flight 写请求。

## 初步搬迁清单

### 需要搬迁的内容

| 内容 | 建议搬迁方式 |
| --- | --- |
| Space 定义 | 从 meta 导出 space name、partition_num、replica_factor、vid_type 等，目标集群重放 `CREATE SPACE` 或调用 meta API |
| Tag schema | 从 meta 导出字段、类型、默认值、NULL 约束、TTL 等，目标重建 |
| Edge schema | 同 tag schema |
| 原生 Tag Index / Edge Index | 导出 index 定义，目标重建；是否先建 index 还是导入后 rebuild 需确认 |
| Vertex 数据 | `StorageClient.scanVertex(space, part, tag, cols)` 分片导出，目标 `INSERT VERTEX` |
| Edge 数据 | `StorageClient.scanEdge(space, part, edge, cols)` 分片导出，目标 `INSERT EDGE`，保留 src/dst/rank/type/props |
| 用户 | 通过 meta API 或 graph nGQL 导出用户账号信息，目标创建 |
| 密码 | 需要确认是否允许导出 encoded password；现有高层 `listUsers` 不含密码字段 |
| 角色/权限 | 通过 meta API 或 nGQL 导出用户角色、space 权限，目标重放授权 |
| IP whitelist / 用户限制 | 如果 Nebula Graph 3.8 商用版启用，需要一并导出 |
| Zone / Group | 如果 space 使用 zone/group，需要确认是否作为逻辑拓扑搬迁 |
| Manifest / checkpoint / error report | 工具自身生成，不属于源集群内容，但必须作为交付物 |

### 不搬迁的内容

| 内容 | 原因 |
| --- | --- |
| job 运行信息 | 已明确排除 |
| 全文索引 | 已明确排除 |
| 配置参数 | 已明确排除 |
| 快照文件 | 物理备份文件，不走本方案 |
| 日志文件 | 运行日志，不属于逻辑数据 |
| storage host 地址、leader、raft membership | 这是目标集群自己的物理状态，不应照搬源集群 |

## 仍需确认的问题

### 1. 冻结窗口覆盖范围

当前答复是“导出前数据禁止，导出后关闭数据禁止”。但如果导出后源集群恢复写入，而目标还在导入，那么“迁移完成后目标与源完全一致”只能理解为“目标与导出快照一致”，不能理解为“目标与当前源集群一致”。

需要确认：

1. 源集群是只冻结到导出完成，还是冻结到导入、校验、业务切换全部完成？
2. 目标集群的一致性验收对象是“导出完成时刻的源集群快照”，还是“验收时刻的源集群当前状态”？

### 2. 内核数据静止范围

需要确认数据静止只禁止 DML，还是也禁止 DDL 和后台数据变更。

建议至少明确以下操作是否禁止：

1. `INSERT`
2. `UPDATE`
3. `UPSERT`
4. `DELETE`
5. `CREATE/ALTER/DROP TAG`
6. `CREATE/ALTER/DROP EDGE`
7. `CREATE/DROP INDEX`
8. `CREATE/DROP SPACE`
9. `BALANCE`
10. `COMPACT`
11. `REBUILD INDEX`
12. TTL 过期清理

### 3. in-flight 写入处理

开启冻结时，已经到达 graphd 或 storaged 的写请求需要明确处理语义。

需要确认：

1. 已经进入 graphd 的写请求是等待完成、直接拒绝，还是尝试回滚？
2. 已经进入 storaged 的写请求是等待完成、直接拒绝，还是尝试回滚？
3. 冻结命令返回成功时，是否保证所有 graphd 和 storaged 都已经进入只读状态？
4. 冻结命令返回成功时，是否保证冻结前已受理的写入都已经完成或失败？

### 4. 冻结状态持久化

需要确认冻结状态是否需要持久化。

典型场景：

1. meta 服务重启后，冻结状态是否继续生效？
2. graph 服务重启后，冻结状态是否继续生效？
3. storage 服务重启后，冻结状态是否继续生效？
4. 新增 graphd 实例后，是否自动继承冻结状态？
5. 新增 storaged 实例后，是否自动继承冻结状态？

### 5. 目标集群初始状态

需要确认目标集群是否必须是空集群。

建议默认要求目标集群无业务数据。否则幂等和“不错误覆盖”会变复杂。

需要确认：

1. 如果目标集群已有同名 space，是报错退出、跳过、比对，还是覆盖？
2. 如果目标集群已有同名用户，是报错退出、跳过、比对，还是覆盖？
3. 如果目标集群已有 schema，是报错退出、跳过、比对，还是覆盖？
4. 如果目标集群已有数据，是报错退出、跳过、比对，还是覆盖？

### 6. 密码搬迁语义

需要确认密码搬迁的目标。

问题：

1. 是否要求目标用户使用与源集群完全相同的密码登录？
2. 是否允许迁移后统一重置密码？
3. 如果必须保持相同密码，是否允许工具读取并导出 `encoded_pwd` 这类敏感字段？
4. 包含用户密码 hash 的导出文件是否必须加密？
5. 密码 hash 是否需要单独脱敏展示，避免进入普通日志？

### 7. 原生索引导入顺序

原生 Tag Index / Edge Index 的重建顺序需要确认。

候选方案：

1. 先建 index 再导入数据：写入慢，但导入完成后索引立即可用。
2. 先导入数据，再创建 index 并 rebuild：导入快，但需要额外 rebuild 阶段，且 rebuild 完成前索引不可用。

需要确认默认采用哪种方案。

### 8. 全量一致与默认校验口径

当前答复同时包含：

1. 目标集群必须在迁移完成后与源集群完全一致。
2. 默认采用数量一致和抽样一致作为检查标准。
3. 额外提供全量 checksum 功能，但是需要手动开启。

这里存在验收口径 GAP：数量一致和抽样一致不能证明完全一致。

需要确认：

1. 迁移任务默认成功条件是否只要求数量一致和抽样一致通过？
2. 生产验收是否必须开启全量 checksum？
3. 如果不开启全量 checksum，是否允许报告中明确标记“未证明全量完全一致”？

### 9. 特殊数据类型一致性

第 27 点目前还未明确。

需要确认以下类型是否要求 canonical 编码后字节级一致：

1. `float`
2. `double`
3. `NaN`
4. `-0.0`
5. `date`
6. `time`
7. `datetime`
8. `timestamp`
9. `NULL`
10. 空字符串
11. 包含换行、逗号、引号、反斜杠等复杂转义字符的字符串

该问题会直接影响 CSV/JSON 格式设计、checksum 设计和验收标准。

### 10. 热生效调速方式

需要确认热生效参数的管理方式。

建议通过配置文件热加载控制以下参数：

1. 导出并发数
2. 导入并发数
3. scan batch size
4. insert batch size
5. 内存队列大小
6. 限速 QPS
7. 限速 bytes per second
8. 重试次数
9. 重试退避时间
10. 单 partition 最大并发

需要确认这种方式是否符合预期，还是希望通过 nGQL/admin 命令动态调整。

### 11. 中间文件压缩和加密

20 亿点边规模下，CSV/JSON 原文会非常大。

建议：

1. 默认支持分片文件。
2. 默认支持 gzip 压缩。
3. 如果包含用户密码 hash 或敏感业务数据，支持 AES 加密。

需要确认：

1. CSV/JSON 文件是否默认压缩？
2. 是否需要强制加密？
3. 文件加密密钥如何提供和管理？
4. 文件是否需要单独生成 checksum 和签名？

### 12. 测试数据集口径

当前答复建议使用 5000 万左右体量开源数据集验证。

需要确认：

1. 是否接受 benchmark generator 生成数据，例如 LDBC SNB？
2. 是否必须使用已经公开下载的真实数据集？
3. 测试数据是否需要覆盖多 space、多 tag、多 edge、索引、TTL、权限、字符串 VID、整数 VID？

## 优先确认问题

建议优先确认以下问题，再进入正式设计方案定稿：

1. 冻结窗口是到导出完成，还是到导入、校验、业务切换全部完成？
2. 数据静止需要禁止哪些 DML、DDL 和后台任务？
3. 目标集群是否必须为空？
4. 密码是否必须保持原密码，是否允许导出 encoded password？
5. 生产验收是否必须开启全量 checksum？
6. 特殊数据类型是否要求字节级一致？
