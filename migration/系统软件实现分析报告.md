## 1. 系统目标与实现范围

工具将源图空间的 Tag/Edge 数据导出为 CSV，再读取 CSV，通过 INSERT 写入新目标空间。它支持配置不同源、目标连接，也支持在同一数据库实例中从空间 A 搬迁到空间 B。

当前实现以正确性和可理解性为优先：搬迁层逐个表处理、逐条 INSERT，并在完成后重新扫描验证；没有实现迁移任务的断点续传、失败自动恢复或高并发调度。底层 StorageClient 扫描仍可能使用多个工作线程，这与搬迁层的顺序调度不矛盾。

核心正确性目标为：

> 在源数据稳定、源数据满足输入约束、目标独占以及扫描接口完整返回数据的前提下，目标的受支持 Schema、完整点边标识与属性值，必须和导出基准一致；migrate 还要求重新扫描的源与该基准一致。

支持的持久化属性类型共 14 种：BOOL、INT8、INT16、INT32、INT64（含 INT 别名）、FLOAT、DOUBLE、STRING、FIXED_STRING、DATE、TIME、DATETIME、TIMESTAMP、DURATION，以及正常 NULL。GEOGRAPHY 不在范围内。

迁移对象是“带 Tag 的点记录”和“边记录”。同一个 VID 上的多个 Tag 分别迁移。索引、账号、权限、物理存储布局、历史版本和集群运行配置不属于当前迁移对象。

主要依据：[模块说明](README.md)、[MigrationEngine 类说明](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L50)。

## 2. 总体架构与模块职责

### 2.1 系统组件

~~~mermaid
flowchart LR
    CLI["MigrationCli 命令入口"] --> E["MigrationEngine 搬迁协调"]
    E --> M["MetaClient 读取 Schema"]
    E --> S["StorageClient 扫描数据"]
    E --> G["GraphConnection 执行 nGQL"]
    S --> V["原生 Value"]
    V --> C["ValueCodec 编码"]
    C --> B["CSV 与 manifest.json"]
    B --> D["预检与解码"]
    D --> G
    G --> T["目标空间"]
    B --> Q["完整键与属性比较"]
    T --> R["重新 scan 目标"]
    R --> Q
    S --> Q
~~~

三个数据库访问角色分工如下：

| 访问组件 | 职责 |
|---|---|
| MetaClient | 获取空间属性、Tag/Edge 清单和属性 Schema |
| StorageClient | 通过 scanVertex/scanEdge 获取原生数据 |
| GraphConnection 内的 Session | SHOW CREATE、CREATE、USE、参数化 INSERT，以及测试中的 FETCH |

Storage 的实际节点地址由客户端通过 Meta 信息获得。CLI 每侧配置一个 Graph/Meta 主机地址，当前未提供 Storage 地址映射或 SSL 的命令行选项。

### 2.3 一次 migrate 的调用结构

总入口 [migrate()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L172) 的主体为：

~~~java
exportSpace(sourceSpace, directory);
importSpace(directory, targetSpace);
return verifySourceAndTarget(directory, targetSpace);
~~~

方法之间通过导出目录传递数据。导出后的内存结果不会直接绕过 CSV 写入目标；importSpace 会重新加载并检查导出文件，因而 CSV 编码/解码链路本身属于实际搬迁路径。

## 3. 命令入口与运行配置

### 3.1 CLI 命令与 Java API 的差别

实现位置：[MigrationCli.execute()](src/main/java/com/vesoft/nebula/migration/MigrationCli.java#L42)。

| CLI 命令 | 实际调用 | 检查对象 |
|---|---|---|
| export | exportSpace | 读取源并产生文件，不验证目标 |
| inspect | 静态 inspect → loadBundle | 仅检查本地导出包，不连接数据库 |
| import | importSpace → verify | 创建目标、导入，再验证目标与 CSV |
| verify | verifySourceAndTarget | 同时验证源、目标与 CSV |
| migrate | exportSpace → importSpace → verifySourceAndTarget | 完整搬迁及双侧验证 |

需要区分：**Java API 的 verify() 只验证目标，而 CLI 的 verify 命令会验证源和目标。** Java API 的 importSpace() 本身只负责导入；CLI import 才会继续调用目标验证。

CLI 在成功时输出 JSON，并为 import、verify、migrate 写入 verification-report.json。发生普通异常时打印原因链并以退出码 1 结束。缺参数、未知参数和重复参数会被拒绝。

### 3.2 配置与默认值

| 配置 | 默认值或规则 |
|---|---|
| source-host / target-host | 127.0.0.1 |
| Graph / Meta 端口 | 9669 / 9559 |
| 用户 | root |
| scan-limit | 100，必须大于 0 |
| timeout-ms | 60000，CLI 要求大于 0 |
| schema-wait-ms | 20000，CLI 要求不小于 0 |
| 密码 | 环境变量读取，CLI 没有默认密码 |

密码可由 source-password-env / target-password-env 指定环境变量名；未指定时，优先使用对应的 NEBULA_SOURCE_PASSWORD / NEBULA_TARGET_PASSWORD，否则使用 NEBULA_PASSWORD。密码不会写入清单或校验报告。

连接配置代码：[connection()](src/main/java/com/vesoft/nebula/migration/MigrationCli.java#L93)。

同库搬迁时，源、目标主机和端口相同，空间名不同。跨集群配置有代码支持，但本目录保存的真实验收主要证明同一实例 A → B 的路径。

## 4. 元数据与内存数据模型

### 4.1 SchemaManifest：使 CSV 的每一列有确定含义

清单模型分为三个层次：

| 层次 | 主要字段 | 用途 |
|---|---|---|
| 空间 | sourceSpace、vidType、partitionNum、replicaFactor、charset、collation | 重建目标空间的主要配置 |
| 表 | kind、name、file、createStatement、columns、rowCount、sha256 | 定位 Tag/Edge、重建 Schema、检查文件 |
| 列 | name、type、nullable、defaultExpressionBase64、commentBase64 | 固定列顺序、类型、NULL 规则及 Schema 比较 |

formatVersion 固定为 1。valueEncoding 标记当前协议为 N/V:Base64、浮点 raw-f64-hex、时间整数数组。

defaultExpressionBase64 保存 Meta 返回的原始编码表达式，用于精确比较；重建 Schema 实际执行的是 SHOW CREATE 返回的 createStatement，不直接执行这段 Base64。

showCreateSpace 保存原空间的 SHOW CREATE 文本，但创建目标空间时只根据所列字段重新拼装 CREATE SPACE，没有直接执行或逐字比较整个 showCreateSpace。

### 4.2 Schema 获取与排序

[describe()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L291) 读取空间配置和所有 Tag/Edge 名称。名称先通过 TreeSet 排序，再按“Tag 在前、Edge 在后”构建清单。

[table()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L325) 保留各属性的 Schema 顺序，生成形如 0000_tag.csv、0001_tag.csv 的文件名。这些编号映射保存在清单中，文件名不会直接采用可能含特殊字符的 Tag/Edge 名称。

内部 Tag ID / Edge 类型数字不作为跨空间身份基准；工具按名称映射，这允许目标重新分配内部编号。

### 4.3 完整键与记录集合

内存中的主要结构为：

~~~java
Map<String, Map<String, String>>
~~~

逻辑示意如下，其中内部实际存储的是编码值：

~~~text
外层：TAG/person
    内层：encodedVID → 完整 CSV 行

外层：EDGE/knows
    内层：encodedSrc,encodedDst,encodedRank → 完整 CSV 行
~~~

内层使用 TreeMap，获得确定的输出顺序，并以唯一键检查重复记录。排序依据是编码字符串，不是数值 VID 的大小。

| 对象 | 完整逻辑身份 |
|---|---|
| Tag 记录 | Tag 名称 + VID |
| Edge 记录 | Edge 名称 + src + dst + rank |

同一 VID 的多个 Tag 会分开处理；相同端点的不同 rank 边会分开处理。出现重复完整键时抛异常，不允许覆盖后继续报告成功。

实现位置：[key() 与 tableKey()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L552)。

## 5. 导出流程

导出入口：[exportSpace()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L71)。

### 5.1 执行步骤

1. 检查空间名，创建输出目录，并要求目录为空。
2. 创建 Graph 和 Meta 访问对象，读取源 Schema。
3. 扫描所有 Tag/Edge，将规范编码后的记录放入内存。
4. 再次读取 Schema，确认导出期间没有观察到结构变化。
5. 为每个表写 CSV，包含表头和所有记录；空表也写表头。
6. 记录 CSV 行数和 SHA-256。
7. 最后写 manifest.json，作为正常导出完成的标志。

CSV 使用 US-ASCII 写入，每条记录以 LF 结束。manifest.json 使用 UTF-8。文件以 CREATE_NEW 创建，避免覆盖已有文件。

这里的“最后写清单”是应用层完成标志，不是数据库事务或文件系统原子提交：进程在写清单时异常退出，仍可能留下不完整文件，后续必须通过 loadBundle 预检。

### 5.2 扫描与列映射

[scanAll()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L210) 按清单逐个扫描 Tag/Edge。返回属性列表由 Schema 构造，持续消费迭代器，要求每页结果非空对象且 isAllSuccess() 为真。

~~~java
while (iterator.hasNext()) {
    ScanVertexResult page = iterator.next();
    require(page != null && page.isAllSuccess(),
            "Incomplete vertex scan: " + table.name);
    collect(page.getDataSets(), table, manifest.vidType, rows);
}
~~~

[collect()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L251) 根据 DataSet 中的列名建立索引，再按清单顺序取得所需字段。它查找完整的“表名.字段名”，避免依赖返回列的偶然顺序。

点记录取 _vid 与全部属性；边记录取 _src、_dst、_rank 与全部属性。遇到重复列、缺列或值数量不匹配会停止。空行集合直接跳过；无属性 Tag/Edge 仍保留其标识列。

### 5.3 原始字节为何没有提前丢失

搬迁工具使用新增的 getDataSets() 取得原始 Thrift Value。STRING 数据走 Value.getSVal() → byte[] → Base64，不经过 Java String 解码，也不进行 Unicode 归一化。

元数据名称确实会按 UTF-8 解码；这与属性数据的字节传输路径不同。普通 STRING 中的 NUL、CR/LF、emoji、组合字符、非法 UTF-8 都由原始字节表达。

scan-limit 只影响扫描每分区每轮的分页量，不限制最终导出的总行数，也不限制搬迁进程的总内存。当前导出会先保存整个扫描结果，再写文件。

## 6. CSV 协议与类型编码

### 6.1 文件结构与单元格协议

表头由 [header()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L543) 生成：

~~~text
Tag： _vid,p0,p1,...
Edge：_src,_dst,_rank,p0,p1,...
~~~

p0、p1 等按清单列顺序映射到真实属性名。类型也来自清单，CSV 单元格中不再重复保存类型标签。

统一格式：

~~~text
N                    正常数据库 NULL
V:<标准 Base64>      非 NULL 值
~~~

Base64 带必要填充且不换行。单元格中没有逗号、双引号或真实 CR/LF，所以当前协议可以用逐行读取与 split(",", -1) 解析。它是专用的规范 CSV 格式，导入器没有实现任意带引号 CSV 的通用解析规则。

### 6.2 全部受支持属性类型

以下“载荷”指 V: 之后的 Base64 解码结果。

| 属性类型 | 载荷 | 原生 Value | 主要规则 |
|---|---|---|---|
| BOOL | ASCII true / false | bVal | 不接受其他文本拼写 |
| INT8 | 十进制 ASCII | iVal | -128…127 |
| INT16 | 十进制 ASCII | iVal | -32768…32767 |
| INT32 | 十进制 ASCII | iVal | -2147483648…2147483647 |
| INT64 / INT | 十进制 ASCII | iVal | 完整 signed 64-bit 范围 |
| FLOAT | 16 位小写十六进制 ASCII，表示扫描值的 raw64 | fVal | 还需满足 float32 精确提升约束 |
| DOUBLE | 16 位小写十六进制 ASCII，表示 raw64 | fVal | 保留正负零和有限数位模式 |
| STRING | 原始字节 | sVal | 允许 NUL 和无效 UTF-8 |
| FIXED_STRING(n) | 原始字节 | sVal | n 为 1…32767；按字节限长；拒绝 NUL |
| DATE | [year,month,day] | dVal | 年为 signed int16，并检查实际日历日期 |
| TIME | [hour,minute,second,microsecond] | tVal | 时分秒合法；微秒 0…999999 |
| DATETIME | [year,month,day,hour,minute,second,microsecond] | dtVal | 日期与时间字段分别验证 |
| TIMESTAMP | Unix 秒的十进制 ASCII | iVal | 0…9223372036 |
| DURATION | [months,seconds,microseconds] | duVal | 月和微秒为 int32，秒为 int64；不归一化 |

整数与时间数组都采用规范十进制：不接受 +1、01、-0、1.0、科学计数法或空格。TIME/DATETIME 不接受第 60 秒。DURATION 的微秒是独立有符号 int32 字段，不套用 TIME 的 0…999999 约束。

编码：[ValueCodec.encode()](src/main/java/com/vesoft/nebula/migration/ValueCodec.java#L39)。
解码：[ValueCodec.decode()](src/main/java/com/vesoft/nebula/migration/ValueCodec.java#L105)。
范围与结构检查：[checkInteger() 等辅助方法](src/main/java/com/vesoft/nebula/migration/ValueCodec.java#L213)。

### 6.3 NULL、空字符串与错误值

| 原始值 | 单元格 |
|---|---|
| 正常 NULL | N |
| 空字节串 | V: |
| 字面字符串 N | V:Tg== |
| 字面字符串 NULL | V:TlVMTA== |
| abc + NUL + def | V:YWJjAGRlZg== |

只有 NullType.__NULL__ 可以编码为 N。数据库返回的其他错误 NULL 状态、Java null 或未设置字段的 Value 都会被拒绝，避免把读取异常当成合法数据。

是否允许某个属性为 NULL，由 Schema 和 MigrationEngine.validateCells() 检查；VID/rank 始终不能为 NULL。

### 6.4 FLOAT / DOUBLE 的精确处理

编码取 Double.doubleToRawLongBits(value.getFVal())，转换为补齐 16 位的小写十六进制 ASCII，再做 Base64。**Base64 编码的是 16 个文本字节，不是直接编码 IEEE 754 的 8 个字节。**

解码采用 Long.parseUnsignedLong(hex, 16) 和 Double.longBitsToDouble(...)。没有经过浮点十进制格式化或 JSON 数字转换。

| 数据 | 扫描值的 raw64 十六进制 | CSV 单元格 |
|---|---|---|
| FLOAT 的 0.1，读出为 float32 提升后的 double | 3fb99999a0000000 | V:M2ZiOTk5OTlhMDAwMDAwMA== |
| DOUBLE 的 0.1 | 3fb999999999999a | V:M2ZiOTk5OTk5OTk5OTk5YQ== |
| +0.0 | 0000000000000000 | 由该 16 字符载荷编码 |
| -0.0 | 8000000000000000 | 由该 16 字符载荷编码 |

FLOAT 源库已按单精度保存，工具保留的是扫描所得实际值，无法恢复写入源库前已被舍入掉的小数位。

[validateReplayableFloat()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L463) 进一步限制精确回放：

- 拒绝会被当前 Thrift 写入器规范化的非规范 NaN 位模式。
- FLOAT 必须是有限值，且 double → float → double 后 raw64 不变。
- DOUBLE 的规范 NaN 和正负无穷没有被该函数统一禁止；能否由目标服务端精确保存仍取决于实际写入和最终比较，历史真实验收没有证明所有非有限值都能往返。

因此，Codec 能表示一个位模式，不等于已经证明目标数据库可精确接收它。

### 6.5 时间字段与 DURATION

时间值按原生字段保存，不使用默认时区的日期字符串格式化，也不把微秒降为毫秒。

DURATION 示例：

~~~text
原生对象：new Duration(259204, 500006, 2)
CSV 载荷：[2,259204,500006]
单元格：V:WzIsMjU5MjA0LDUwMDAwNl0=
~~~

载荷顺序为“月、秒、微秒”；Thrift 构造器顺序为“秒、微秒、月”。解码明确调整了位置。月份不会按固定天数折算，负号和混合符号也不会被改写。

### 6.6 规范性检查的意义

decode 会对 Base64 解码后重新编码，要求和原文本一致；validateCells 再要求 encode(decode(cell)) 与原单元格一致。这使同一受支持值有确定表示，便于之后直接比较整行字符串。

这种检查能够发现非法或不规范输入，但不能单独证明编解码实现没有共同错误。独立原生值测试用于补充这部分证据，见第 12 节。

## 7. 导入流程与 nGQL 生成

导入入口：[importSpace()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L106)。

### 7.1 导入前检查

[loadBundle()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L381) 在建立目标连接前检查整个导出包：

| 检查 | 失败时阻止的问题 |
|---|---|
| 版本、编码标记、VID 类型和表清单 | 按错误协议解释文件 |
| 文件名、文件存在、非符号链接、SHA-256 | 读取错误文件或变化后的内容 |
| 表头、列数、行数 | 缺列、错列或缺行 |
| 完整键唯一性 | 重复记录在 INSERT 时互相覆盖 |
| 原生类型、整数范围、NULL 约束 | 不合法或可能被隐式改写的值 |
| 浮点可重放性、最小 rank | 已知无法精确写回的值 |

单元格错误包装了 CSV 文件名和行号。预检不访问数据库，也不会创建目标空间。

SHA-256 用于检查文件是否匹配清单，它不是签名认证。清单内包含后续要执行的建表语句；当前代码只做有限的身份和格式检查，应使用可信来源的导出包。

### 7.2 创建目标 Schema

预检通过后的步骤为：

1. 字符串 VID 场景，先检查目标字节字面量的解析能力。
2. SHOW SPACES，要求目标空间不存在。
3. 根据清单创建目标空间。
4. 等待 Schema 缓存传播，执行 USE。
5. 执行所有 Tag/Edge 的 createStatement。
6. 再次等待并读取目标 Schema，进行一致性检查。
7. 逐表、逐行执行 INSERT。

Schema 等待是固定时长 sleep，默认 20 秒，不是主动探测“所有节点已就绪”，也不是失败重试机制。时间不足时后续操作会报错，当前不会自动重试创建和导入。

### 7.3 属性值参数化

[parameters()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L480) 将每个单元格解码为原生 Value，并按 v0、v1、v2…放入参数 Map。

[insertStatement()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L491) 按清单列顺序生成 INSERT：

- Tag 的 v0 是 VID，属性参数从 v1 开始。
- Edge 的 v0/v1/v2 是 src/dst/rank，属性参数从 v3 开始。
- 所有属性显式赋值，包括 NULL，不依赖目标再次计算默认值。
- 无属性记录仍生成带空属性列表的 INSERT。

实际执行调用 Session.executeWithParameter，见 [GraphConnection.execute()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L711)。Base64、浮点十六进制和时间数组都先还原成原生值，不会原样拼入属性字面量。

### 7.4 VID 与 rank 的服务端兼容

当前适配了历史验收中本地 3.6 服务端的行为：INSERT 的 VID 位置不接受参数，因此标识使用严格生成的 nGQL 表达式。

[vidLiteral()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L608)：

| VID | 生成形式 |
|---|---|
| 普通整数 | 精确十进制文本 |
| 最小 INT64 | toInteger("-9223372036854775808") |
| 字符串 | 每个非零原始字节分别写为三位八进制转义 |

例如 user1 生成 "\165\163\145\162\061"。字符串 VID 不会先按 UTF-8 解码，非法 UTF-8 字节也可保持原样。

[verifyStringLiteralSupport()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L639) 通过只读 YIELD 验证 1…255 的全部字节，确保目标解析结果与预期 byte[] 一致；验证不通过时在创建目标空间前失败。工具不自动修改服务端配置。

[rankLiteral()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L630) 使用十进制，但拒绝 Long.MIN_VALUE。当前工具可回放 rank 范围为 -9223372036854775807…9223372036854775807；INT64 属性和 VID 的完整上下边界不受这个 rank 限制影响。这个拒绝目前是固定规则，不会按服务端版本自动放宽。

## 8. 一条记录的完整往返示例

下面是与当前协议一致的教学示例，不是本次新写入数据库的记录。

假设 Tag person 有三个可空 STRING 属性：s、empty、nullable。VID 为 user1，属性值为：

~~~text
s        = 字节 61 62 63 00 64 65 66，即 abc + NUL + def
empty    = 长度为 0 的字节数组
nullable = 正常 NULL
~~~

### 8.1 scan 与导出

scan 返回各属性的原生 Value。collect 按清单排列列顺序，并调用 ValueCodec.encode。

CSV 为：

~~~csv
_vid,p0,p1,p2
V:dXNlcjE=,V:YWJjAGRlZg==,V:,N
~~~

清单说明 p0 对应 s、p1 对应 empty、p2 对应 nullable，三列类型均为 STRING。CSV 自身没有真实 NUL 或换行字符混入单元格。

### 8.2 解码与 INSERT

导入后的属性参数：

~~~text
v1 = Value.sVal(原始七字节数组)
v2 = Value.sVal(空字节数组)
v3 = Value.nVal(NullType.__NULL__)
~~~

对应 INSERT 形态：

~~~ngql
INSERT VERTEX `person`(`s`,`empty`,`nullable`)
VALUES "\165\163\145\162\061":($v1,$v2,$v3);
~~~

这里的参数由客户端单独发送，属性中的 NUL 不需要再做 nGQL 文本转义。

### 8.3 回读与比较

目标 scan 回来的七个字节重新编码为 V:YWJjAGRlZg==，空字节数组重新编码为 V:，NULL 重新编码为 N。完整行与 CSV 相同才通过。

如果 s 被改为 abc，或者 empty 被改为 NULL，对应的规范单元格都会变化，最终比较会报属性不一致。

边记录采用同样的属性处理方式，只是前面多出 src、dst、rank 三个身份字段。例如：

~~~csv
_src,_dst,_rank,p0
V:dXNlcjE=,V:dXNlcjI=,V:Nw==,V:YSxi
~~~

它表示 user1 → user2、rank 为 7、属性为字节字符串 a,b。

## 9. 一致性验证的实现与边界

### 9.1 三份数据与比较顺序

CSV 是导出基准 E，目标重新扫描得到 T，源重新扫描得到 S。verifySourceAndTarget 先比较 T 与 E，再比较 S 与 E，全部通过才生成成功报告。

实现：[verifySourceAndTarget()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L164)、[compareCluster()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L187)。

~~~text
对每个 Tag/Edge：
    Schema 必须匹配
    实际记录数必须等于 CSV 记录数
    CSV 中每个完整键必须存在于实际扫描结果中
    同键对应的完整规范行必须逐字相同
~~~

每个集合先要求完整键唯一；在此基础上，记录数相同且所有基准键都存在，可以确定键集合相同。整行规范编码再确认属性的字节、位模式和原生字段表示相同。

这一检查不依赖 SHOW STATS 的历史统计，不只比较总行数，也不使用 nGQL 浮点近似相等。

### 9.2 Schema 实际比较了什么

[assertSchemasEqual()](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L364) 比较：

- 空间 VID 类型、charset 和 collation。
- Tag/Edge 数量、按名称排序后的清单。
- 每个 Tag/Edge 的 SHOW CREATE 文本。
- 属性列表的类型、顺序、可空性、默认表达式和注释。

分区数和副本数用于创建目标，但不在此比较方法中逐项核对；整个 SHOW CREATE SPACE 文本也未参与比较。索引等未导出对象不会被纳入一致性结论。

SHOW CREATE 采用精确文本比较：跨版本如果仅文本格式变化，也可能被判为不一致。当前没有实现跨版本 Schema 语义归一化。

### 9.3 成功报告的含义

[VerificationReport](src/main/java/com/vesoft/nebula/migration/VerificationReport.java#L8) 只有在比较方法成功返回后才创建：

| 字段 | 含义 |
|---|---|
| matched | 本次规定范围内的比较全部通过 |
| sourceRechecked | 是否也检查了源与 CSV；CLI import 为 false |
| verifiedAt | 本次验证完成时生成的时间 |
| tagRows | 各 Tag 的行数之和，不是去重后的点数 |
| edgeRows | 各 Edge 的完整记录数之和 |
| rowsByTable | 按 TAG/名称、EDGE/名称给出的记录数 |

工具不会在 Java 验证失败时返回 matched=false 的报告对象，而是抛异常；CLI 随后退出码为 1。旧的成功报告文件不会因为后续验证失败而自动删除，使用报告时应结合本次退出码和 verifiedAt，不能把旧文件当成本次成功结果。

### 9.4 比较能够证明与不能证明的事情

在前提成立时，比较证明源/目标扫描可见的受支持记录集合与导出基准相同。

它不构造事务快照，也不锁定源或目标。重新扫描不能发现所有“中途改变、随后又恢复”的情况；源仍必须在整个过程保持停写和 Schema 稳定，目标必须独占。

如果扫描层在源和目标都以同样方式遗漏数据，单靠重扫比较也不能提供独立的全库完整性证明。当前通过扫描回归测试和已知样本的独立 FETCH 断言来增加证据，但运行时仍依赖 scan 的正确性以及“源不存在无 Tag 点”等外部约束。

## 10. 异常处理、资源与超时

### 10.1 失败后的状态

| 失败阶段 | 处理方式与可能留下的状态 |
|---|---|
| Schema 或扫描 | 抛异常；输出目录可能已创建 |
| CSV / manifest 写入 | 抛异常；可能留下部分文件，必须重新预检 |
| 导入包预检 | 创建目标空间之前失败 |
| 目标建表或 INSERT | 抛异常；已创建的空间、表和记录保留 |
| 一致性比较 | 抛异常，不能宣布迁移成功 |
| CLI 结果报告写入 | 即使数据已导入，也可能因报告写入失败而返回退出码 1 |

逐条 INSERT 的错误会包装表身份和记录序号，并说明目标空间不完整。这个序号来自按键排序后的处理顺序，不应直接等同于物理 CSV 文件行号；loadBundle 的解析错误则包含物理行号。

没有跨所有 INSERT 的事务，也没有自动回滚。对失败目标重复执行 import 会受到“目标已存在”检查阻止。

### 10.2 资源所有权

GraphConnection 管理自己的 NebulaPool 和 Session；close 时先释放 Session，再关闭池。Meta 包装类管理独立 MetaClient。scanAll 在 finally 中关闭 StorageClient，文件读写使用 try-with-resources。

MigrationEngine.close() 是空实现，因为 Engine 本身不保留跨操作使用的连接。资源主要由每个具体操作内部创建和关闭。

代码位置：[GraphConnection](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L689)、[Metadata](src/main/java/com/vesoft/nebula/migration/MigrationEngine.java#L728)。

搬迁层未设计数据重试、恢复或幂等调度，但这不等于底层客户端绝对不会进行任何连接尝试或 Leader 重定向。不要把“没有迁移失败重试功能”理解为修改了所有 SDK 内部重试行为。

### 10.3 timeout 的真实作用

搬迁 CLI 的 timeout-ms 同时传入相关客户端配置。此次对 [StorageClient.connect()](../client/src/main/java/com/vesoft/nebula/client/storage/StorageClient.java#L106) 增加了一行：

~~~java
config.setTimeout(timeout);
~~~

否则扫描连接池配置保持默认 0，而 [GraphStorageConnection.open()](../client/src/main/java/com/vesoft/nebula/client/storage/GraphStorageConnection.java#L43) 会执行：

~~~java
int newTimeout = timeout <= 0 ? Integer.MAX_VALUE : timeout;
~~~

因此未传入时，实际配置可能变成约 24.86 天，而非调用者期望的 60 秒。严格说不能把这里描述为“无限超时”。

当前普通 TCP 路径把值传给 Socket 连接与读取超时。它是底层操作的超时，不是整个 RPC、一次扫描或整个搬迁的总时限；也不会给 CountDownLatch.await 或连接池借用等待自动增加统一截止时间。SSL 分支还有预先 createSocket 的过程，不能推定该参数完整限制了所有 SSL 建连阶段。

本次报告只核对了上述代码链路，没有实施网络故障注入，也没有通过等待 24.86 天验证该行为。

## 13. 当前实现约束与工程取舍

| 项目 | 当前状态 | 使用影响 |
|---|---|---|
| 源停写、Schema 稳定、目标独占 | 外部前提；工具不加锁 | 重扫不能代替一致性快照 |
| 无 Tag 的点 | 不枚举、不自动证明不存在 | 源必须事先排除此类点 |
| 普通 STRING 任意字节 | 原生 byte[] 与 Base64 传递 | 不做 UTF-8 替换或 Unicode 归一化 |
| FIXED_STRING / VID 含 NUL | 代码拒绝可见 NUL，源还需预先排除 | 若服务端读取前已截断，客户端无法恢复原值 |
| GEOGRAPHY、活跃 TTL | 明确拒绝 | 不会自动转换或停用 TTL |
| 最小 INT64 rank | 固定拒绝 | 不能把它当成成功迁移覆盖 |
| 超大字符串 | 协议未写死业务长度上限 | 实际受服务端、RPC 和 JVM 内存约束 |
| 整个扫描结果 | 保存在内存 TreeMap | 分页不会让总内存变成常量 |
| 逐条 INSERT | 搬迁层顺序执行 | 实现简单，吞吐未做专门优化 |
| 跨版本 Schema 文本差异 | 精确比较 | 可能因格式差异提前失败 |
| 失败目标 | 保留部分数据 | 需要检查后另选新目标或人工处理 |
| SSL、地址映射、多 Graph 地址 | CLI 未暴露 | 跨网络部署需要额外适配 |
| 导出包真实性 | 无签名机制，建表语句来自清单 | 使用可信导出包 |
| 运行中总时限 | 未实现 | socket timeout 不等于任务 deadline |

若把总记录数记为 N、编码后的全部数据量记为 B，主要内存占用随 B 与记录对象数量增长。TreeMap 插入包含按键比较的对数开销；超长键会增加比较成本。Base64 载荷通常约为原字节数的 4/3，Java 字符串、树节点、解码副本和同时保留的基准/扫描集合还会进一步增加占用，因此不能按 CSV 文件大小直接估算全部堆内存。

当前 import 和 verify 都会重新加载导出包；verifySourceAndTarget 会在保留基准的同时依次扫描目标和源。这个取舍符合当前“不优先考虑高性能”的目标，但不能称为流式、恒定内存的搬迁实现。
